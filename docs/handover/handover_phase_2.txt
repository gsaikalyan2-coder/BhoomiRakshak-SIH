B.3  DECISIONS MADE THIS SESSION
  D1  THREE MIGRATIONS, NOT ONE. 0001 reference / 0002 domain / 0003
      intelligence+governance+view. Each is independently reversible and the
      downgrade path was exercised (`alembic downgrade base` then
      `alembic upgrade head`) three times during the build.

  D2  ALL THIRTEEN TABLES ARE CREATED NOW, including risk_scores, risk_reasons,
      recommendations, alerts, annotations and audit_log which nothing writes to
      until Phase 3/6/7. Rationale: the schedule has no slack; a migration
      written on Wednesday is a migration that breaks the demo.

  D3  status_log DOES NOT CONTAIN A FULL STAGE HISTORY.
      This was discovered while building the E2 view and it changes how E2 and
      N7 must be implemented. The dataset records the desk chain WITHIN each
      project's CURRENT stage only: every project has exactly one open row
      (is_current = true, exited_on = NULL), and every status_log row for a
      project carries the SAME stage as projects.approval_stage. There are
      4,518 rows over 900 projects — about five DESKS per project, not five
      stages.
      Consequence: a view that asks "when did the Award stage end" can never
      return a date, because the file only ever appears in the stage it is
      sitting in now. The first draft of issue_resolutions did exactly that and
      returned zero cleared dates for five of six issue classes. It was rewritten.

  D4  issue_resolutions CLEARS BY STAGE PROGRESSION, AND STATES ITS EVIDENCE.
      Statutory order used (LARR 2013): SIA Completed(0) -> Section 11
      Notification(1) -> [objection(2)] -> Award Declared(3) -> Compensation
      Disbursement(4) -> R&R Implementation(5) -> Possession Taken(6).
      An issue class ranked BELOW the project's current approval_stage is
      Cleared; equal is "Open — at desk"; above is "Not reached".
      Dates are taken only where the source records actually carry one:
        notification  -> projects.notification_date
        objection     -> status_log: date the file left the Legal Cell desk
        possession    -> projects.actual_completion_date
        the class immediately before the current stage
                      -> status_log: date the file entered the current stage
      Every other cleared class returns is_cleared = true with cleared_on NULL
      and evidence = 'stage passed — clearance date not captured in the source
      records'. NO DATE IS EVER INVENTED. The view exposes an `evidence` column
      and the UI must show it.
      Result over the 600 closed projects: 1,738 dated clearances
      (notification 409, objection 332, award 95, compensation 97, R&R 98,
      possession 600).

  D5  DISTRICT BOUNDARY POLYGONS ARE DERIVED, AND LABELLED AS SUCH.
      PROJECT_PLAN.md Phase 1 §2 says "District boundary GeoJSON loaded for the
      choropleth". No GeoJSON ships with dataset rev 3 and downloading one was
      not possible in this session. Rather than leave Phase 7's choropleth with
      no geometry, district_boundaries is populated as
      ST_Buffer(ST_ConvexHull(ST_Collect(village centroids)), 0.05) per district,
      with a `source` column set to 'derived-village-hull'.
      THIS IS AN APPROXIMATION AND IS AN OPEN ITEM — see B.5.

  D6  DEMO PASSWORD SCHEME. Each officer's password is their own officer_id in
      lowercase (e.g. TN-LAO-2024-0456 -> "tn-lao-2024-0456"), hashed with
      bcrypt (passlib, $2b$, 12 rounds). The shipped password_sha256_demo column
      is DROPPED in the loader and never reaches the database. Phase 4 shows two
      demo credentials on the login screen by design.

  D7  'None' IS A VALUE, NOT A NULL. projects.legal_dispute_stage contains the
      literal string "None" meaning "no dispute on file" — it is ordinal level 0
      in the Phase 2 encoding. pandas read it as NaN and the load failed on a
      NOT NULL constraint. seed.py now restores it explicitly. PHASE 2 MUST NOT
      REINTRODUCE THIS BUG when it reads the same CSV.

  D8  spatial_index=False on every GeoAlchemy2 Geometry column. GeoAlchemy2
      creates its own idx_<table>_geom automatically, which duplicated the
      explicit GiST indexes (six indexes for three columns). Explicit index,
      auto-index off.

  D9  succession_risk.csv IS LOADED AS A TABLE (362 rows, one per parcel with a
      claim). It is application data, never a model input — that decision is
      unchanged and re-stated in C.4 below.
